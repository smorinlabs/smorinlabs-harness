1. The problem

You have N markdown documents covering the same territory — research notes, design drafts, README variants, spec revisions. They overlap. They contradict in places. Some sections are unique to one document; others are word-for-word duplicates across several.

You want a smaller number of consolidated outputs (often just one) with three properties:

  1. Zero information loss. Every unique fact, code sample, value, and recommendation present in any source must survive or be explicitly logged as intentionally omitted with a reason.
  2. Auditable synthesis. Every non-trivial judgment call — choosing source A's wording over source B's, picking one version pin over another — must be traceable to its sources and reviewable later.
  3. Reverifiable originals. The source files must remain byte-identical somewhere accessible, so the merge can be re-audited months later against exactly what it saw.

A naïve approach — open the files, write a new doc — fails all three quietly. You don't know what you dropped. You can't reconstruct why you chose what you chose. By the time you want to check, the originals may have been edited or deleted.

2. At a glance — the five artifacts

Every merge produces (or operates on) five named artifacts. Each has a single role. Two are immutable inputs, two are synthesized outputs, two are audit logs, and one is a verification gate. (Five artifacts, six roles — the consolidated docs are both outputs and the substrate the audit logs annotate.)

immutable input synthesized output audit log verification gate
Solid arrows: artifact A is needed to produce or constrain artifact B. Dashed red arrow: the byte-identical verification gate run at the end of the merge. The archive and SHA manifest are produced at opposite ends of the workflow but tie together by this single check.

3. The workflow — 8 phases on a timeline

The workflow is a strict sequence of eight phases. Each phase produces or modifies one or more artifacts. The diagram below shows which phase touches which artifact, and what verification gate (if any) runs at each step.

Time flows left to right. A dark colored bar = the artifact is being created or modified in that phase. A light colored bar = the artifact exists and is being read/referenced. Red dots = validate.sh is run as a gate.

Phase-by-phase

  1. Pre-flight snapshot. Compute SHA-256 of every source file. Write to .source-sha256-pre-merge.txt. This is the only verifiable baseline; without it, Phase 8 cannot prove anything.
  2. Topic-to-source map. Extract every heading from every source with its line range. For each planned output section, bind it to its contributing source file(s) and line range(s). Save as the first section of decisions-and-conflicts.md.
  3. Skeleton outputs. Write the section structure of each consolidated doc — headings only, empty bodies. Forces architectural decisions before any synthesis happens.
  4. Validation script. Drop in the marker↔entry round-trip enforcer. First run reports 0/0 PASS. This is the gate for every subsequent phase.
  5. Merge content. Fill each skeleton from the mapped source ranges. Log every non-trivial synthesis as a CFL entry. Mark each entry's location inline at the end of the synthesized block. Run validate.sh after each output doc completes.
  6. Cross-references. If multiple output docs, link between them using GitHub anchor rules. Verify every anchor resolves.
  7. Coverage audit. Dump every source heading. For each one not in the topic-to-source map, add an entry to Intentionally omitted source sections with a reason. No silent drops survive this gate.
  8. Archive and verify. git mv originals to archive/. Diff SHA-256 of the archive against the Phase 1 baseline — must be zero diff. Run validate.sh one final time.

4. Inside each artifact

This section is the heart of the document. For each artifact, we show: what it contains, what logic produces it, what consumes it downstream, and a representative snippet.

input source-*.md (N source files)

Purpose

The raw inputs to the merge. Multiple markdown documents with overlapping content. Never modified during the workflow — the inviolable-originals guarantee depends on it.

Logic

None. These are user inputs. The workflow only reads them.

What consumes it

  • Phase 1 computes SHA-256 over each file to write the baseline manifest.
  • Phase 2 reads each file to extract headings for the topic-to-source map.
  • Phase 5 reads the mapped line ranges to produce the merged content.
  • Phase 7 re-reads every heading for the coverage audit.
  • Phase 8 moves them to archive/ via git mv.

Snippet (illustrative)

# Observability on GCP — A Tracing-First Guide

## Google Cloud's observability stack
Cloud Trace is where spans land …

## Distributed tracing from first principles
A trace represents a single end-to-end request …
audit log consolidated/.source-sha256-pre-merge.txt

Purpose

A frozen baseline of every source file's byte-content, captured before any merging starts. The single source of truth for "what the originals were when the merge began."

Logic

One line per source file. Each line is shasum -a 256 output: a 64-character hex digest, two spaces, and the relative path. Sorted for deterministic comparison. Written once in Phase 1; never modified again.

What consumes it

  • Phase 8 verification. After archiving, the workflow computes SHA-256 of every archived file and diffs the result against this baseline. Any non-empty diff means a source file was modified during the merge — a violation of the inviolable-originals guarantee.

Why the file is hidden (leading dot)

The manifest is bookkeeping, not content. Hiding it from default ls output keeps the consolidated/ directory listing focused on the user-facing outputs. It is committed to git as a regular file — hidden in the filesystem, visible in version control.

output consolidated/*.md (the merged documents)

Purpose

The user-facing result. One or more markdown documents containing the synthesized content from the sources, organized into the section structure decided in Phase 3.

Logic

Each output doc is structured as a series of sections (typically ## top-level, ### subsections). Each section is filled with content from the source line ranges mapped to it in Phase 2's topic-to-source map. When a synthesis combines material from multiple sources, the merged paragraph ends with an inline HTML comment marker: <!-- CONFLICT: CFL-XXX -->. The marker points at the corresponding entry in decisions-and-conflicts.md.

Marker placement rule

Markers go at the end of the synthesized block, never at the start. The reader sees the content first, then the audit pointer. This is the single most common review violation; reviewers will flag it and require a fix.

What consumes it

  • The user — this is what the merge is for.
  • validate.sh — greps for CFL-XXX markers to verify each has a matching log entry.
  • Phase 7 coverage audit — indirectly: the topic-to-source map is the contract, and reviewers verify each mapped range is represented in the merged content.

Snippet

## 5.7 Context propagation to downstream services

The `propagation.inject()` call writes both `traceparent` and
`X-Cloud-Trace-Context` headers because we configured a
`CompositePropagator`. The downstream service extracts these headers,
and the full request flow appears as a single trace in Cloud Trace.
<!-- CONFLICT: CFL-013 -->

The marker on the last line points at CFL-013 in the decisions log — the entry there explains which source the synthesis came from and what was chosen.

audit log consolidated/decisions-and-conflicts.md

Purpose

The complete audit log for the merge. Holds three distinct things: a topic-to-source map (the contract), a list of CFL entries (the per-decision log), and a list of intentionally-omitted source sections (the coverage receipt).

Structure

The file is divided into three top-level sections, written in this order:

  1. Topic-to-source-section map — one table per output doc, binding each section to source file(s) and line ranges.
  2. Intentionally omitted source sections — bullet list, one entry per source section not in the map, with a reason.
  3. CFL entries — one entry per non-trivial judgment call, each with stable ID and six standard fields.

Logic

The map is written in Phase 2 from heading extraction. CFL entries are appended in Phase 5 as decisions arise; IDs are monotonic and gap-free. The intentionally-omitted log is filled in Phase 7 from the coverage audit's diff between source headings and the topic-to-source map.

What consumes it

  • validate.sh — greps ### [ ] CFL-XXX and ### [x] CFL-XXX entries to verify every one has an inline marker.
  • Phase 5 reviewers — read the topic-to-source map to verify each mapped range is represented in the merged content.
  • Future readers — the user, months later, auditing why a decision was made.

verification gate consolidated/validate.sh

Purpose

Enforces the round-trip between the inline CFL-XXX markers in the merged docs and the ### [ ] CFL-XXX entries in the audit log. Fails (exits non-zero) if either side has an unmatched ID.

Logic

  1. Grep every CFL-XXX ID out of inline <!-- CONFLICT: CFL-XXX --> markers across all merged docs. Sort and dedupe — call this set markers.
  2. Grep every ### [ ] CFL-XXX or ### [x] CFL-XXX heading out of the decisions log. Sort and dedupe — call this set entries.
  3. comm -23 markers entries — markers without entries (audit pointer goes nowhere).
  4. comm -13 markers entries — entries without markers (log entry orphaned).
  5. If either is non-empty, print the offending IDs and exit 1. Otherwise print PASS: N markers and N entries (all matched) and exit 0.

Why bash and not a Python script

The check is pure set algebra over text patterns — grep | sort | comm is the minimal toolset and has zero dependencies. The skill ships validate_round_trip.sh that runs anywhere a POSIX shell does.

What it does not check

The script verifies structural round-trip — that every ID has a partner on both sides. It does not check that the CFL entry text is correct, that the marker is placed at the end of the block, that the synthesis is sound, or that the entry's source line ranges are accurate. Those require human review.

Snippet — what running it looks like

$ bash validate.sh
PASS: 27 markers and 27 entries (all matched)

$ bash validate.sh   # after adding an entry but forgetting the marker
FAIL: log entries without matching inline markers:
  - CFL-028
output archive/*.md (the preserved originals)

Purpose

The original source files, moved (not copied) out of their working location after the merge is verified complete. The archive lets future readers re-verify the merge against the exact bytes the merge saw.

Logic

In Phase 8, each source file is moved to archive/ via git mv (so rename history is preserved). After the move, SHA-256 of each archived file is computed and diffed against the .source-sha256-pre-merge.txt baseline. The diff must be empty.

The byte-identical guarantee

If the post-archive sums differ from the pre-merge baseline by even a single byte, a source file was modified during the merge. This is treated as a hard failure — investigate and revert before proceeding. The guarantee is not "the originals are still readable" — it is "the originals are bit-for-bit unchanged."

What consumes it

  • Future re-audits — a reader can compare CFL excerpts in the log against the original lines in archive/ at any time.
  • git revert workflow — if the merge is later found wrong, git revert on the archive-move commit restores the originals to their working location.

5. The three invariants the design enforces

The five artifacts exist to enforce three invariants. Each invariant has a single mechanical check that proves it.

Invariant 1 — every judgment call is auditable both ways

Every CFL-XXX marker in a merged doc has a matching entry in the log, and every entry has a matching marker in a doc. No orphans on either side.

Enforced by: validate.sh (Phase 4 onwards).

Failure mode it prevents: writing an audit entry that refers to no specific paragraph, or marking a paragraph as "see CFL-014" when no such entry exists.

Invariant 2 — originals are bit-for-bit unchanged

The SHA-256 sums of the archived originals, computed in Phase 8, exactly match the sums of the source files captured in Phase 1.

Enforced by: diff baseline post-archive-sums.txt at the end of Phase 8.

Failure mode it prevents: silently editing a source file during the merge (intentionally or accidentally), losing the ability to re-audit against what the merge actually saw.

Invariant 3 — every source heading is accounted for

Every #, ##, and ### heading in any source file appears in exactly one of two places: the topic-to-source map (it contributed to an output section), or the intentionally-omitted log (it was duplicate or unneeded, with a stated reason).

Enforced by: the Phase 7 coverage audit. The skill ships coverage_audit.sh which dumps every heading for manual diff against the two lists.

Failure mode it prevents: silently dropping a section of source content because no reviewer noticed it was missing from the merge.

The deeper pattern: the workflow does not try to verify the merge is correct. It verifies it is complete (no information lost) and auditable (every choice can be re-examined). Correctness still requires human review — but those three mechanical invariants raise the floor of what's possible to check automatically.

6. Why this is good design

Every promise is mechanically verifiable

"No information was lost" is normally a human claim. Here it decomposes into three specific, scriptable checks: SHA round-trip, marker↔entry round-trip, and heading coverage. Software trusts evidence, not assertions.

Each artifact is load-bearing

Phase 1 produces the SHA manifest that Phase 8 consumes. Phase 2 produces the topic map that Phase 7 audits against. Phase 5 produces markers that Phase 4's script enforces. Nothing exists for its own sake — every artifact closes a verification loop somewhere later.

Right-sized abstractions

Stable CFL IDs are three digits and monotonic — cheap to assign but durable for cross-referencing in review comments months later. Inline markers are HTML comments — invisible in rendered output, greppable in source. The validation script is 50 lines of bash, not a framework.

Pre-mortem orientation

Phase 1 (SHA snapshot) and Phase 3 (skeletons before content) both happen before any destructive work. The workflow assumes you will make mistakes and builds the audit infrastructure first.

Self-policing structure

The validation script is the lever that makes the rest of the discipline automatic. A human can write a marker and forget the log entry — the script catches it. A human can write a log entry and forget the marker — the script catches it too.

Reviewable in pieces

Subagent-driven execution dispatches one task per phase or per output doc, with two-stage review after each. Reviewers see small focused diffs against a known spec instead of one giant merge.

7. Why this is expensive design

Every property above costs something. The workflow earns its weight on large, conflict-heavy merges. On small or low-conflict merges, the same machinery is overhead.

Heavy for what most merges actually look like

Eight phases, five artifacts, two-stage review per phase. For merging two README variants of 60 lines each, you spend more time on audit infrastructure than on the merge itself. The lite path exists for this reason, but the cognitive default is the full path.

Structural, not semantic, verification

The validation script confirms every marker has a log entry. It does not confirm the log entry is correct. A reviewer can write "I synthesized A and B by choosing A" while actually having chosen B, and every mechanical check still passes.

The topic-to-source map is hand-built

Phase 2 is the most time-consuming and worst-scaling phase. With 7 sources it takes an hour; with 70 it takes a week. There is no tooling here — just reading and table-writing.

CFL classification is subjective

"Non-trivial synthesis, conflict, or judgment call" is the rule. Reviewer A logs every paragraph that merges two sources; Reviewer B only logs paragraphs where the sources disagreed factually. Both are defensible; both produce different log densities.

Stable IDs are a maintenance promise

Once CFL-014 is written, it cannot be renumbered. Retired entries accumulate. Small but real cognitive overhead in long-lived merges.

Cross-references rot silently

Markdown anchors are derived from heading text. Rename a heading and every cross-reference breaks — no error, no warning, just a link landing at the top of the page. Manual verification only.

Coverage audit is reactive

Phase 7 detects missing source content at the end. Earlier feedback would be ideal — per-doc, not whole-merge — but the audit is structured as a final gate.

Markdown-only, Unix-only

The validation script assumes grep -E, comm, sort, shasum. Marker syntax assumes HTML comments inside markdown. Anchor rules assume GitHub-flavored markdown. Porting to RST, AsciiDoc, or DOCX is non-trivial.

Subagent overhead

Three dispatches per task (implementer + spec reviewer + code-quality reviewer) is expensive. Phase 1 (SHA snapshot) does not need a code-quality review. A more granular policy would help.

8. When to use vs. when to skip

Use full pathUse lite pathDon't use this skill
≥3 source documents 2 short, low-conflict sources One document needs editing, not merging
Conflicting facts, recommendations, or values across sources Mostly complementary content, minimal overlap Sources are in a non-markdown format and you don't want to convert
You will reference the merge result months later Quick one-time consolidation You don't need to verify nothing was dropped
Multiple people will review or extend the result You're the only consumer A diff tool plus a manual edit pass is sufficient

The honest claim is not "this is the right way to merge documents." It is: "this is the right way to merge documents when you cannot afford the merge to be wrong and cannot prove it later." Most of the time, that condition does not hold. When it does, the workflow earns every minute of its overhead.
